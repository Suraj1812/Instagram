# Instagram (local-only edition)

[![CI](https://github.com/Suraj1812/Instagram/actions/workflows/ci.yml/badge.svg)](https://github.com/Suraj1812/Instagram/actions/workflows/ci.yml)
[![EAS Build](https://github.com/Suraj1812/Instagram/actions/workflows/eas-build.yml/badge.svg)](https://github.com/Suraj1812/Instagram/actions/workflows/eas-build.yml)

An Instagram-inspired app with **no backend of any kind**. There is no
server, no REST API, no Firebase/Supabase, no cloud database, and the app
makes zero network requests. SQLite plus the device filesystem *is* the
entire application layer — every screen reads and writes directly to them.

## Why this works

- **Auth is local.** Signing up hashes your password (SHA-256 + per-account
  salt via `expo-crypto`) and stores it in SQLite. Logging in re-hashes and
  compares. The active session is just a user id in `expo-secure-store`.
  Multiple local accounts can coexist on one device.
- **"Uploading" a post is a file copy.** `mediaStorage.ts` resizes/compresses
  the image with `expo-image-manipulator` and copies the result into
  `FileSystem.documentDirectory` — permanent, private, on-device storage.
  There's no upload step to wait on, so publishing feels instant.
- **The feed, reels, explore grid, search, profiles, DMs, and notifications
  are all SQL queries against local tables.** No caching layer is needed
  because there's nothing upstream to cache *from* — SQLite is the source of
  truth, full stop.
- **First launch seeds a believable demo network** (`seedData.ts`): 12 demo
  accounts with generated avatar/post/story images and a handful of short
  synthetic video clips (all bundled as static assets, copied into local
  storage once), a follow graph, likes, and comments — so the app doesn't
  open to an empty void. When you sign up for real, your new account
  auto-follows a few demo accounts and gets a welcome DM, so Home/Messages/
  Notifications all have content immediately.

## Architecture

```
src/
  db/
    schema.sql              full local schema — this IS the backend
    database.ts              connection + migrations + resetDatabase()
    repositories/            the ONLY place raw SQL lives
      userRepository, postRepository, commentRepository,
      storyRepository, messageRepository, notificationRepository,
      searchRepository (FTS5), metaRepository (kv store)
  services/
    localAuth.ts             signup/login/session, all on-device
    mediaStorage.ts           image/video "publish" = resize + copy to disk
    seedData.ts               first-launch demo network generator
    seedAssets.generated.ts  static require() list for bundled seed media
  store/                     zustand — thin orchestration over repositories
  theme/                     dark/light tokens, persisted via kv_meta
  navigation/                Onboarding -> Auth -> 5-tab main app
  screens/                   one folder per feature area (see below)
  components/                LocalImage, Avatar, PostCard, StoryBar, etc.
```

### Screens (all connected, nothing is a dead end)

- **Onboarding** -> **Login/Signup** (local accounts)
- **Home** — feed from people you follow, stories bar, pull to refresh,
  infinite scroll, double-tap to like, opens Notifications/Messages
- **Stories** — full-screen viewer with per-account progress bars and
  per-viewer seen state; **Create Story** to publish your own
- **Explore** — grid of posts from accounts you don't follow yet, ranked by
  engagement, plus a suggested-accounts row; search bar opens **Search**
  (FTS5, instant, local)
- **Reels** — vertical swipeable video feed using `expo-av`, like/save/
  comment-count actions
- **Create Post** — pick a photo or video from the library; videos publish
  as Reels automatically
- **Profile** (yours or anyone's) — stats, follow/message actions, post/reel
  grid tabs, **Followers/Following** lists, **Edit Profile**
- **Notifications** — likes, comments, follows, generated by the actions
  above (and by seed data)
- **Messages** — conversation list + **Chat**, instant local send
- **Settings** — theme toggle, on-device storage usage, reset-all-data,
  logout

## Running it

```bash
npm install
npx expo start
```

No environment variables, no API keys, no backend to stand up — the app is
fully functional offline from the first launch.

**Important:** as of this update the app uses `react-native-webrtc` for
calling, which is a native module. **It will not run in the plain Expo Go
app** — Expo Go only supports the modules Expo ships by default. You need a
"development build" or a real standalone build instead:

```bash
npx expo prebuild          # generates native android/ (and ios/) folders
npx expo run:android       # builds + installs a debug dev-client on a connected device/emulator
```

## CI/CD

Two GitHub Actions workflows live in `.github/workflows/`:

- **`ci.yml`** — runs on every push/PR to `main`. Mirrors the exact
  verification chain used to build this project: installs dependencies,
  type-checks the whole codebase in strict mode with zero tolerance for
  dead code, validates `app.json` resolves (this is what would have caught
  the config-plugin bug from earlier), generates native Android *and* iOS
  projects via `expo prebuild`, and does a full Metro bundle export for
  both platforms. If any of these steps fail, the app genuinely wouldn't
  build for a real user either — this isn't a rubber-stamp pipeline.
- **`eas-build.yml`** — builds the real installable `.apk` via Expo's cloud
  build service. This **will not run successfully until you add one
  secret yourself** — `EXPO_TOKEN`, tied to your own free Expo account.
  I have no way to create this for you; the workflow file has the exact
  4-step setup in its comments. Once added, trigger it manually from the
  Actions tab, or push a tag like `v1.0.0` to trigger it automatically.

## Building an installable APK yourself

I can't produce an APK from this sandbox — there's no Android SDK, emulator,
or signing keychain here, only a Linux shell with Node/Python. But the
project is set up so you can generate one in about 10 minutes using Expo's
free cloud build service:

```bash
npm install -g eas-cli
eas login                        # free Expo account
eas build -p android --profile preview   # builds a real, installable .apk
```

When it finishes, EAS gives you a download link (and a QR code) for the
`.apk` — send that link to any Android phone, open it, and Android will
prompt to install (you'll need to allow "install unknown apps" for whichever
app you download it through — that's a standard Android security gate for
anything outside the Play Store, not something specific to this app, and no
app config can bypass it). The `preview` profile in `eas.json` is already
configured to output a `.apk` rather than the Play-Store-only `.aab` format.

**iOS is a separate build system entirely** — an `.apk` will never install
on an iPhone. Getting this app onto an iPhone requires a Mac with Xcode, an
Apple Developer account ($99/yr), code signing, and either TestFlight or
`eas build -p ios`. There's no single artifact that installs on both
platforms.

## Calling (WebRTC, no server)

Voice/video calls use `react-native-webrtc` for real peer-to-peer media —
this is genuine WebRTC, not a mock. The catch, explained in
`src/services/webrtcCall.ts`: WebRTC still needs a one-time "signaling"
handshake (trading an SDP offer/answer and ICE candidates) before two
devices can connect, and that handshake normally goes through a server. With
zero backend, that handshake happens manually instead — the caller generates
a text "connection code," sends it to the other person any way they like
(paste it in chat, read it aloud, AirDrop it, or show/scan a QR code if
you're in the same room — both are built in, with an automatic fallback to
text if a code is too long to scan reliably). Once that's done once,
audio/video flows directly device-to-device with no server involved. Only STUN (public, run by Google) is configured,
not a TURN relay — calls between phones on very restrictive NATs may fail to
connect, since fixing that requires a relay server, which is out of scope
here. I have not been able to test this against a second physical device in
this environment, so treat it as implemented-and-should-work rather than
verified-working.

## Branding

This is a lookalike in layout and interaction patterns, not a copy of
Instagram's actual brand assets — the name, wordmark, and icon here are
original. I can't build something using Instagram's real logo/name designed
to be indistinguishable from the genuine app; that crosses from
"inspired-by" into trademark/brand impersonation, which carries real risk
(especially for something distributed as an installable file to other
people, since apps wearing someone else's identity are also the standard
pattern for phishing).

## Designed to add a backend later, without one now

The repository layer is the seam: every screen calls a repository function
(`getFeedPage`, `toggleLike`, `sendMessage`, ...), never SQL directly and
never a network client directly. If a backend is ever wanted, the swap is
localized to `src/db/repositories/*` (e.g. have `toggleLike` also POST to an
API, or replace SQLite reads with a synced cache) — screens, stores, and
navigation wouldn't need to change. Nothing in this codebase does that today;
it's a structural choice, not a feature.

## What I actually verified (and how)

I don't have an Android/iOS emulator or physical device in my environment,
but I do have Node and network access to the npm registry, so this round I
went further than reading the code — I actually:

1. Ran `npm install` for real (~1,190 packages).
2. Ran the TypeScript compiler (`tsc --noEmit`) against the entire project,
   with `strict` mode and `noUnusedLocals`/`noUnusedParameters` — **zero
   errors, zero dead code**, after fixing several real bugs it caught
   (wrong import source in `LocalImage.tsx`, a mistyped WebRTC event API,
   dead state in `CreatePostScreen`, a config-resolution setting).
3. Ran `expo config` — this caught a real, build-breaking bug: `app.json`
   listed `react-native-webrtc` as a config plugin, but that library
   version doesn't ship one, so every build would have failed immediately.
   Fixed (its permissions were already declared manually, so no plugin was
   needed at all).
4. Ran `expo prebuild` for **both** Android and iOS — this generates the
   real native projects and is where config-plugin and native-linking bugs
   surface. It caught a second real issue (`userInterfaceStyle` needs
   `expo-system-ui`, which wasn't installed) — fixed. Confirmed via
   `react-native config` that every native module (webrtc, svg, reanimated,
   gesture-handler, screens, safe-area-context, pager-view, flash-list,
   get-random-values) autolinks correctly, and that all camera/microphone/
   storage permissions merged into the real `AndroidManifest.xml` and
   `Info.plist`.
5. Ran a full `expo export` for both platforms — this invokes the actual
   Metro bundler against all 1,931 modules, and confirmed all 87 bundled
   seed assets (avatars, posts, stories, reel videos) resolve correctly by
   their generated `require()` paths and package into a working Hermes
   bytecode bundle with no errors or warnings.

That's real, tool-verified confidence that the app installs its
dependencies, resolves its config, generates valid native projects on both
platforms, and bundles its JavaScript without errors — which rules out an
entire class of "doesn't even build" failures.

## Honest limitations

- **Compiler/bundler-verified, not device-verified** (see above) — the
  build pipeline works end to end; on-device behavior is correct by review,
  not by observation.
- **Seed videos are synthetic** (generated via `ffmpeg` test patterns), not
  real footage — they exist to make Reels functional and demonstrable, not
  to look good. Anything you record or pick yourself uses real video.
- **Single-device only, by design.** Nothing syncs between two phones —
  there is no channel for that without a server, which was explicitly out
  of scope here.
- Push notifications, end-to-end encrypted messaging, and multi-device
  handoff aren't implemented — they all require infrastructure this app
  deliberately doesn't have.
- Video call quality/reliability will vary a lot with network conditions
  since there's no TURN relay to fall back on.
